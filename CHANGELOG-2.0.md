# Changelog for 2.0 (branch changelog)

**This is the changelog of the branch `feature/plugin-system`.** It lists what this branch changes compared with `main`, for the later major version 2.0. Nothing here is released. The changes of the 1.x releases stay in [CHANGELOG.md](CHANGELOG.md), which this branch does not edit, so merging `main` into the branch causes no conflict there. When 2.0 is released, these entries move into `CHANGELOG.md` as the section `[2.0.0]` and this file is removed.

The design is described in [docs/plugin-concept.md](docs/plugin-concept.md); the README changes for 2.0 are collected in [README-2.0.md](README-2.0.md).

## Not yet released

### Added
- **Plugins:** checks tied to specific software move out of the main script into files of their own (`plugins/<name>.sh`), shipped with the release. Each plugin runs in a `bash` process of its own with an empty environment, gets the new lines of its logs on stdin and the settings it declares, and answers with `TEXT`, `NOTE` and `ALERT` lines. A plugin only reads: it writes no files and makes no network connections. Alerts, summary, `--only`, state files and everything that needs the network stay in the main script.
- **Only the plugins of the release run.** The main script holds the SHA-256 of `lib/plugin-lib.sh` and of every plugin. A file that is missing, changed or not in the list is not run and raises an alert; so do a plugin that fails or runs too long. The files and their directories must belong to root and must not be writable by others, like the configuration file.
- `PLUGINS_OFF` (new setting, default empty): names of plugins that should not run. Shipped plugins are on by default, so an update never drops a check silently.
- **Tests** for the plugin framework (`tests/plugins.bats`): checksums, header, protocol and limits, failing and hanging plugins, and a rule check that plugins contain no network or changing commands. The workflow checks `lib/`, `plugins/` and `tools/` with ShellCheck too.
- **`--self-update`:** installs the latest release in one step – only when root runs it by hand, never from cron. It downloads the release archive, `SHA256SUMS` and its signature `SHA256SUMS.sig`, checks the signature with the maintainer's public key built into the script (`ssh-keygen -Y verify`, OpenSSH 8.1 or newer; on older systems such as RHEL 8 it asks before going on with the checksum only, and refuses with `--yes`), checks the checksum and that the archive holds only plain files and folders, unpacks it next to the installation, tests the new version without running it (syntax, version number), shows the changes since the installed version (without terminal control characters), asks, lets the new version check its plugin files (`--verify`) and only then swaps the folders – nothing of the new version runs before the answer. Downloads only over HTTPS, at most 20 MB per file. The previous version stays in `/usr/local/lib/plesk-server-report.old`; `--self-update --rollback` goes back. It replaces only an installation unpacked from the release archive, not a git checkout or the single file of 1.x.
- `--self-update` stays within its major version (the newest 2.x release; `--self-update --major` is reserved for the next one and says so), refuses to run without a terminal (never from cron, also not with `--yes`), and names a newer major version. Taken over from the `--self-update` of 1.12.0 on `main`, so both behave alike; the daily update check compares with the newest release of the own major version, too.
- `--verify`: checks that `lib/` and `plugins/` are the files of this release (checksums, and as root their owner and permissions).
- `tools/build-release.sh` (for the maintainer): builds the release archive and `SHA256SUMS` from the committed state and prints the command to sign it.
- Workflow `release` (started by hand in the Actions tab): checks that the version entered is the one in the script, runs `tools/build-release.sh` and puts the archive and `SHA256SUMS` on a draft release with the notes from `CHANGELOG.md`. The signing key never goes to GitHub: `SHA256SUMS` is signed on the maintainer's computer, `SHA256SUMS.sig` is added to the draft, then it is published.
- `tools/update-plugin-sums.sh` (for developing): writes the checksums into the main script after a plugin was changed.

### Changed
- **`panel` is a plugin** (`plugins/panel.sh`). Section `PLESK PANEL LOG`, its lines and its alerts are unchanged; a test compares them with the output of the old function. The name for `--only` and `--list` stays `panel`.
- **`backups` is a plugin** (`plugins/backups.sh`), the first one without a log on stdin. Section `BACKUPS`, its lines and its alerts are unchanged, so `summary.txt` shows the backup status as before. It reads `BACKUP_LOG_DIR` (from 1.11.1) like the old function. The tests of 1.11.1 (`tests/backup.bats`, real anonymized logs) run against the plugin, plus a parity test and a few cases made from the real logs.
- **`webmail` is a plugin** (`plugins/webmail.sh`), the first one with several logs. Its lines stay in the section `MAIL` and its alerts are unchanged, so `summary.txt` counts failed webmail logins as before. The tests of 1.11.1 (`tests/webmail.bats`, real anonymized logs) run against the plugin; hand-written logs (`tests/fixtures/webmail`) add what the real ones don't show – a guessed password, a brute-force attack, mails from abroad. The test with hostile log lines covers it.
- For plugins: a plugin may leave out `PLUGIN_SECTION` and continue the section before it; `PLUGIN_LOGS` may name a file below a directory from the settings (`$SETTING/file`); `ALERT-FOREIGN` (`alert_foreign`) raises an alert only if one of the given IPs is outside `ALLOWED_COUNTRIES` – the main script, which has the GeoIP database, decides.
- **`php-config` is a plugin** (`plugins/php-config.sh`), the first daily one: the scan of `.htaccess`, `.user.ini` and `php.ini` in the document roots moves out of `webshell` into a check of its own (`--only php-config`). It finds the same files and raises the same alerts; in the daily checks it has its own paragraph *PHP settings in .htaccess, .user.ini and php.ini*, and the paragraph of `webshell` covers PHP files only. `WEBSHELL_CHECK=0` switches off both. The time of its last scan is kept in `plugins/php-config/state` instead of `webshell_conf_full`; the first run takes it over from version 1.x, so nothing is scanned or reported twice. README: the example report follows with the other changes for 2.0.
- For plugins: daily plugins (`PLUGIN_SCHEDULE="daily"`, time limit three times `FIND_TIMEOUT`); the context file `domains` (`PLUGIN_INPUTS`: domain and document root, asked from Plesk by the main script); a state (`STATE` lines, stored by the main script in `plugins/<name>/state` – only in a normal run – and handed back as `$PSR_STATE`). `--show-state` shows the plugins' states; STATE-FILES.md describes them.
- A plugin runs with the time zone (`TZ`) of the main script.
- **`wordpress` is a plugin** (`plugins/wordpress.sh`), the last check to move: login attempts (POSTs to `wp-login.php` and `xmlrpc.php`) per domain, successful logins from abroad or after repeated failures, and new PHP files in `wp-content/uploads` – taken out of `web` and the former check `uploads`. **The layout changes:** a section `WORDPRESS (since last run)` after `WEB`; `WEB` has no column *login POSTs* any more, the section `WEBROOTS` is gone. Alert texts are unchanged (a test compares them, the login details and the upload lines with the old functions); successful logins of a domain are listed in IP order. `summary.txt` reads reports of both layouts and stays the same (tested with the stored reports rewritten in the new layout). The time of the last upload scan is taken over from `last_scan`.
- For plugins: `PLUGIN_LOGS` may contain `*` as a whole part of a path (`$VHOST_LOGS/*/logs/access_log`: that log of every domain); a plugin keeps log positions of its own (in `offsets/`, named after its name and the path), so a log the main script reads too is read in full by both. On its first run a plugin starts at the positions the main script stored, so an update from 1.x neither repeats nor misses lines.
- The script no longer consists of one file: `lib/` and `plugins/` must be installed next to it, from the release archive (README: Installation).
- File names with a line break: `php-config` and `wordpress` read file lists separated by NUL, so a folder whose name holds a line break hides no file from them; such a line break is shown as `?`. A plugin's line can't be split into two any more (`out`, `alert`, `note`, `state` turn a line break into a space), so a file name can't forge an alert or a state line.
- The release workflow refuses to build from a branch other than `main`.
- `UPLOADS_PHP_IGNORE` no longer ignores everything in `wp-content/uploads/borlabs-cookie/` by default: Borlabs Cookie keeps no PHP files there, and a webshell placed in that folder went unreported. The log of Mailchimp for WP (`mailchimp-for-wp/debug-log.php`) stays ignored. (Also for `main`.)
